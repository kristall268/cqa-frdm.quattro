# CQA Freedom — подготовка к защите

## 1. Что это за продукт (30 секунд)
Веб-платформа, которая **автоматически оценивает качество диалогов** операторов контакт-центра (чаты и звонки, RU/KZ/EN) по чек-листу из 8 критериев. По каждому критерию система выдаёт **оценку, обоснование и ссылку на конкретную реплику**. Результат можно **обжаловать**, и проверяющий меняет оценку. **Чек-лист редактируется в интерфейсе** без изменения кода.

## 2. Архитектура
```
Браузер (HTML/CSS/JS, :5500) ──REST──> Spring Boot (Java 21, :8080) ──> PostgreSQL 16 (Docker)
                                              │
                                              ├─> API организаторов (импорт диалогов по group_id)
                                              └─> LLM-цепочка: Groq (gpt-oss-120b, qwen3.8-27b, gpt-oss-20b)
                                                               → Gemini → OpenRouter (резерв)
```
| Слой | Технологии | Где в коде |
|---|---|---|
| Frontend | чистый HTML/CSS/JS, без сборки (готов для Dynamics 365) | `frontend/` |
| Backend | Java 21, Spring Boot 3.5, JPA, Flyway | `backend/src/main/java/com/cqafrdm` |
| БД | PostgreSQL 16 (JSONB для транскриптов и результатов) | `db/migration/V1, V2` |
| AI | OpenAI-совместимый клиент, цепочка провайдеров | `evaluation/ai/*` |
| Расчёт баллов | детерминированный `ScoringEngine` | `evaluation/scoring` |
| Выгрузка | `results.json` (формат 1.0) | `results/*`, `scripts/results.py` |

## 3. Как проходит оценка одного диалога (CQA Guard)
1. **Маскирование ПДн:** ИИН, номер карты, телефон, email и IBAN заменяются на `[ИИН]` и т.п. до отправки в облако.
2. **Оценщик** (gpt-oss-120b) получает чек-лист и пронумерованный транскрипт `[i] (время) РОЛЬ: текст` и за один вызов отвечает по всем 8 критериям в JSON: ответ, обоснование, `evidence_ids`, `checked_range`.
3. **Валидатор** проверяет ответ: все ли критерии есть, допустимо ли значение по шкале, разрешён ли N/A, существуют ли указанные реплики, что «Да» подтверждено репликой **оператора**, а не бота. При ошибке делается 1 повтор, затем статус `FAILED`. **Выдуманный балл не ставится никогда.**
4. **Проверяющая модель** (qwen) независимо перепроверяет каждый критерий.
5. **Арбитр** (третья модель) решает **только спорные** критерии большинством голосов. Уверенность: 100% (все согласны), 67% (2 из 3), меньше — передаётся человеку.
6. **Баллы считает код, а не модель:** `итог = 100 × Σ баллов / Σ весов применимых критериев`; N/A исключается, вес перераспределяется; грубая ошибка — отдельный флаг.

## 4. Функции для демонстрации
| Просьба жюри | Где показать |
|---|---|
| Все диалоги с грубыми ошибками и объяснением | Обзор → «Грубые ошибки по типам» или Диалоги → «Грубые ошибки» |
| Оценка конкретного диалога с обоснованием | Карточка → «Оценить AI» → клик по `#реплике` |
| Отправить на апелляцию | Карточка → «Апелляция» → Апелляции → «Изменить» → итог пересчитан, исходная оценка сохранена |
| Изменить чек-лист: добавить критерий, вес | Чек-листы → «Что если?» (пересчёт без AI) → «Сохранить новую версию» |
| Новый набор диалогов | Диалоги → «Импорт группы» → «Оценить группу» → Результаты |

Дополнительно: тёмная и светлая тема (переключатель в шапке), прогресс анализа, результаты по разделам, аудиоплеер с переходом к реплике.

## 6. Вопросы жюри — готовые ответы
1. **Почему баллы не считает модель?** — LLM ошибается в арифметике и непостоянна. Модель выдаёт только ответ и доказательство, балл считает детерминированный код. Поэтому вес меняется мгновенно и без AI.
2. **Как вы боретесь с галлюцинациями?** — Каждое утверждение ссылается на реальный номер реплики. Валидатор отклоняет несуществующие реплики и «Да» без реплики оператора. При двух неудачах — `FAILED`, а не выдуманный балл.
3. **Сколько стоит одна оценка?** — Сейчас бесплатные тарифы, $0. На платном тарифе быстрых моделей это примерно $0.002–0.004 за оценку с проверкой (≈8–12 тыс. токенов на 2–3 вызова).
4. **Почему несколько моделей?** — Независимая перепроверка и арбитраж повышают совпадение с экспертом, а уверенность показывает, где нужен человек.
5. **Локальная или облачная модель?** — Облачная цепочка из 5 провайдеров с автоматическим переключением. Поддерживается гибрид: звонки оценивает локальная модель (Ollama, `LLM_LOCAL_*`), данные не покидают компьютер.
6. **Персональные данные?** — Маскируются перед облаком, ключи хранятся только в `.env` на сервере, в браузере и Git их нет.
7. **Как отличаете N/A от «Нет»?** — Нет: действие требовалось, но не выполнено. N/A: выполнено условие неприменимости из чек-листа. Правило и пример есть в промпте, валидатор запрещает N/A там, где он не разрешён.
8. **Что, если модель недоступна или упёрлась в лимит?** — Переход к следующей модели или провайдеру; если лимит у всех, ожидание 20–60 с и повтор.
9. **Как добавить новый критерий?** — В редакторе, без кода. Новая версия хранится отдельно, старые оценки ссылаются на свою версию. Новый критерий сразу попадает в промпт.
10. **Почему бот не влияет на оценку?** — Бот и система — только контекст; «Да» засчитывается только с репликой оператора.
11. **Как работает апелляция?** — Проверяющий подтверждает или меняет ответ. `ScoringEngine` пересчитывает итог поверх последнего решения, исходная оценка AI неизменна.
12. **Звонки и аудио?** — Оцениваем по готовому транскрипту (STT не требуется). Есть плеер и переход к моменту реплики. Ссылка организаторов на аудио сейчас отвечает HTTP 414.
13. **Насколько точна система?** — Перед prod-набором откалибровали промпт на DEV по ручной экспертной выборке. Неуверенные оценки помечаются для человека.
14. **Масштабирование?** — Batch с ограничением параллельности, повторно не оцениваются уже оценённые, БД PostgreSQL, сервис без состояния.
15. **Почему frontend без фреймворка?** — Требование Guide и интеграция в Dynamics 365 HTML-компонент: без сборки и зависимостей.

## 7. Запуск (коротко)
`docker compose up -d db` → `cd backend && mvnw spring-boot:run` → `cd frontend && python -m http.server 5500` → http://localhost:5500. Подробнее — в `README.md`.
